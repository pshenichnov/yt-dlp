# YouTube Processing Platform Agent Guide

## Purpose

This file defines the working rules, system boundaries, terminology, and quality
expectations for contributors and coding agents working on the YouTube
Processing Platform.

The platform accepts asynchronous REST requests to extract and analyze public
YouTube content. ASP.NET Core services own the public API and workflow
orchestration. RabbitMQ carries commands and events. MassTransit is used by
.NET services. A Python service invokes the `yt-dlp` command-line tool and
communicates with the rest of the system through versioned, language-neutral
JSON messages.

Phase one supports one end-to-end use case:

1. Accept a YouTube video ID or supported YouTube video URL.
2. Create an asynchronous processing job.
3. Extract a manual or autogenerated transcript.
4. Store the transcript in blob storage.
5. Extract the video thumbnail.
6. Store the thumbnail in blob storage.
7. Analyze the transcript.
8. Produce a short description and bullet points describing the subjects
   discussed.
9. Expose job status and the completed result through REST.

YouTube search, comments, audio transcription, bulk processing, semantic
search, and public Internet exposure are outside phase one unless a later task
explicitly adds them.

## Current Implementation

The phase-one vertical slice is implemented under `src`, with local
infrastructure in `compose.yaml`, cross-language examples under `contracts`,
checked-in EF Core migrations, unit tests under `tests`, and operational notes

## Required Technology Choices

### .NET services

- ASP.NET Core Web API for REST endpoints
- A currently supported .NET LTS release selected and pinned at project setup
- MassTransit for .NET messaging
- RabbitMQ as the transport
- Entity Framework Core for PostgreSQL persistence
- OpenTelemetry-compatible logging, metrics, and tracing
- `System.Text.Json` for JSON

### Python extraction service

- Python 3.10 or newer, pinned per service image
- `yt-dlp` invoked as a command-line subprocess
- FFmpeg available in the container image
- `aio-pika` for native RabbitMQ integration
- Pydantic models for message and configuration validation
- An S3-compatible client for blob storage
- Structured JSON logging

### Infrastructure

- RabbitMQ for commands and events
- PostgreSQL for durable service state, inboxes, outboxes, and projections
- S3-compatible blob storage; MinIO is the phase-one local deployment
- Ollama as the default phase-one transcript-analysis provider
- Docker Compose for local development and the initial deployment profile

Do not substitute Redis, Celery, Kafka, an in-process queue, direct HTTP calls
between workflow stages, or the yt-dlp Python API without an approved
architecture change.

## Service Boundaries

### API service

Owns:

- Public REST contracts
- Request validation and canonicalization
- Job creation
- Idempotency keys
- Job-status and analysis-result read models
- Authorization and API rate limits

Does not:

- Run yt-dlp
- Call Ollama directly
- Execute long-running work during an HTTP request
- Read RabbitMQ queue state to determine job status

### Orchestrator service

Owns:

- The video-analysis saga
- Workflow state and transitions
- Stage timeouts
- Command dispatch
- Handling completion, failure, and cancellation events
- Publishing job-status events
- Translation between internal MassTransit contracts and the raw JSON Python
  integration boundary

Does not:

- Store transcript or thumbnail bytes
- Run yt-dlp
- Generate summaries

### Python extractor service

Owns:

- yt-dlp subprocess execution
- Video metadata extraction
- Manual-caption and autogenerated-caption extraction
- Transcript normalization needed to produce an extraction artifact
- Thumbnail extraction
- Uploading extracted artifacts to blob storage
- Python-side inbox/outbox and command idempotency
- Extraction progress and terminal result events

Does not:

- Own the overall API job
- Generate LLM summaries
- Accept arbitrary yt-dlp arguments
- Download the full video in phase one

### Analyzer service

Owns:

- Downloading the transcript artifact
- Transcript-size validation and chunking
- Prompt construction
- Calling the configured analysis provider
- Validating structured analysis output
- Persisting analysis results
- Publishing analysis completion or failure

Does not:

- Run yt-dlp
- Store RabbitMQ messages as the source of truth
- Receive thumbnail or transcript bytes in a message

## Domain Terminology

Use these terms consistently:

- **Job**: the user-visible asynchronous operation.
- **Analysis**: the final result for one video.
- **Command**: an instruction with one logical owner, named in imperative
  verb-noun form.
- **Event**: an immutable statement that something happened, named in past
  tense.
- **Artifact**: a blob-stored file referenced by URI, checksum, content type,
  and size.
- **Transcript source**: `manual_caption` or `automatic_caption` in phase one.
- **Stage**: the current coarse-grained workflow step.
- **Correlation ID**: the job ID used to connect logs, traces, commands, and
  events.
- **Causation ID**: the message ID that caused another message.
- **Extraction version**: a version used to invalidate cached extractor output.
- **Analysis version**: the model and prompt version used to create a summary.

Do not use “request,” “task,” “job,” and “command” interchangeably in code or
contracts.

## Phase-One Functional Rules

### Accepted input

The public API accepts either:

- A YouTube video ID
- A canonical `youtube.com/watch` URL
- A `youtu.be` URL
- A supported YouTube Shorts URL that resolves to one video

The API extracts the candidate video ID and sends only the canonical video ID
across the messaging boundary. The Python service constructs the canonical
YouTube URL itself.

Reject:

- Non-HTTPS URLs
- Non-YouTube hosts
- Playlist-only URLs
- Channel URLs
- Search URLs
- Arbitrary extractor URLs supported by yt-dlp
- Input containing shell fragments or additional command-line options

### Transcript policy

Phase-one selection order is:

1. A creator-provided caption in the requested language
2. An autogenerated caption in the requested language
3. A stable `TRANSCRIPT_UNAVAILABLE` failure

Audio download and Whisper transcription are not part of phase one. Preserve
the service boundary so that a transcription service can be inserted later.

Produce:

- The original caption file, normally WebVTT
- A normalized UTF-8 plain-text transcript
- A structured JSON transcript containing language, source, and timestamped
  segments when timing data is available

The normalized transcript is the analyzer input.

### Thumbnail policy

Retrieve the best available YouTube thumbnail without downloading the video.
Preserve the original image when practical. Store the detected content type,
extension, size, and SHA-256 checksum.

### Analysis output

The analyzer must return a structured result containing:

- A concise description of the video discussion
- Three to ten bullet points
- Analysis language
- Model identifier
- Prompt version
- Analysis timestamp

Do not invent claims that are not supported by the transcript. If the
transcript is too sparse or malformed, fail explicitly rather than returning a
confident summary.

## REST Conventions

- Prefix phase-one endpoints with `/api/v1`.
- Return `202 Accepted` for successfully queued work.
- Return RFC 9457-compatible problem details for HTTP errors.
- Use UTC ISO-8601 timestamps.
- Use opaque GUID job IDs.
- Support an `Idempotency-Key` header on job-creation endpoints.
- Use pagination for collection endpoints.
- Do not return transcript or image bytes inside status responses.
- Return controlled artifact download URLs or API resource URLs.
- Do not expose internal RabbitMQ topology, stack traces, local paths, bucket
  credentials, or yt-dlp command lines in public responses.

Phase-one endpoints are defined in `ARCHITECTURE.md`.

## Messaging Rules

### Internal .NET boundary

Use normal typed MassTransit contracts and the MassTransit JSON envelope for
.NET-to-.NET messages.

### Python integration boundary

Use raw JSON with `Content-Type: application/json`. Configure raw JSON only on
the relevant MassTransit send/receive endpoints.

Every integration message must contain:

- `schemaVersion`
- `messageId`
- `correlationId`
- `causationId` when applicable
- `messageType`
- `occurredAt`
- `payload`

Cross-language JSON property names use lower camel case. Contract schemas live
under the future `contracts/json-schema` directory and are authoritative for
the Python boundary.

### Routing

- Send commands to explicit durable queues.
- Publish events to explicit durable topic exchanges.
- Use versioned queue, exchange, routing-key, and schema names.
- Do not rely on .NET namespaces for Python routing.
- Do not put transcript text, image bytes, audio, or raw yt-dlp JSON into
  RabbitMQ messages when a blob reference is sufficient.
- Keep messages comfortably below 256 KiB; phase-one terminal messages should
  normally be below 32 KiB.

### Delivery semantics

Assume at-least-once delivery:

- Every consumer must be idempotent.
- Use a transactional outbox in .NET services.
- Use durable inbox/outbox records in the Python service.
- Deduplicate using `messageId` and `commandId`.
- Acknowledge RabbitMQ commands only after the result and outbound event are
  durable.
- Use publisher confirms.
- Use bounded retries and dead-letter queues.

Do not claim exactly-once processing.

## Blob-Storage Rules

- Treat object storage as the source of truth for extracted artifacts.
- Store artifact metadata in PostgreSQL.
- Use immutable, versioned object keys.
- Include SHA-256, size, and content type in artifact references.
- Never place bucket credentials in messages or API responses.
- Use server-generated or short-lived presigned download URLs.
- Delete per-command temporary files after successful upload.
- Clean stale temporary files after crashes.
- Keep database, broker, artifact, and temporary storage locations
  configurable.
- Do not encode a particular host filesystem or mount point into object keys.
- For the initial HomeLab profile, keep PostgreSQL and RabbitMQ on reliable
  internal storage; validate the external media filesystem before using it as
  durable blob storage.

## Persistence and Ownership

One PostgreSQL server may host multiple phase-one databases, but each service
must have a separately owned database or schema and credentials.

- API service owns job and result projections.
- Orchestrator owns saga state.
- Extractor owns its inbox, outbox, and extraction records.
- Analyzer owns its inbox, outbox, and analysis records.

Services must not query another service’s tables. Communicate through contracts
or explicit API resources.

## Reliability Requirements

- Set explicit timeouts for yt-dlp, FFmpeg, blob operations, and Ollama.
- Distinguish retryable failures from terminal failures.
- Do not retry invalid input, deleted videos, private videos, or missing
  transcripts indefinitely.
- Use delayed redelivery for network failures and YouTube throttling.
- Stop retries after a configured maximum and publish a stable failure event.
- Preserve already uploaded artifacts when a later stage fails.
- Make terminal events replayable without duplicating the analysis.
- Support graceful shutdown and stop consuming before terminating subprocesses.
- Ensure a service restart does not lose an accepted job.

## Security Rules

- Never use `shell=True`.
- Never concatenate user input into a command string.
- Pass subprocess arguments as an array.
- Run containers as non-root.
- Use a unique temporary directory per command.
- Restrict temporary and output paths to configured roots.
- Validate all downloaded file paths before upload.
- Apply file-size, transcript-size, duration, and execution-time limits.
- Do not log cookies, authorization headers, RabbitMQ passwords, PostgreSQL
  passwords, blob credentials, or LLM API keys.
- Keep YouTube cookies optional and mounted as a secret when later needed.
- Do not expose RabbitMQ, PostgreSQL, MinIO administration, Ollama, or internal
  services directly to the Internet.
- Keep network exposure configurable. The initial HomeLab profile should use a
  trusted private network such as Tailscale rather than router port forwarding.

## Observability

All services must emit structured logs with:

- `service`
- `environment`
- `correlationId`
- `messageId`
- `jobId`
- `videoId` when known
- `stage`
- `event`
- Sanitized error code

Propagate W3C trace context through MassTransit and through explicit integration
headers for Python. Expose health checks separately for liveness and readiness.

Minimum metrics:

- Jobs accepted, completed, failed, and canceled
- Queue depth
- Consumer throughput and failures
- Stage duration
- yt-dlp command duration and exit-code class
- Transcript and thumbnail extraction success
- Blob upload duration
- Analyzer duration and failures
- Retry and dead-letter counts

Do not use yt-dlp stdout as the only source of workflow state.

## Coding Standards

### General

- Prefer small, explicit components over reflection-heavy abstractions.
- Keep transport models separate from domain models and persistence models.
- Validate configuration at startup.
- Use UTC everywhere.
- Pin container base images and major dependencies.
- Treat external command output as untrusted input.
- Avoid hidden network access in constructors and startup registration.
- Add tests with every behavior change.

### C#

- Enable nullable reference types.
- Treat warnings as errors in continuous integration.
- Use cancellation tokens for asynchronous operations.
- Avoid `.Result`, `.Wait()`, and synchronous blocking.
- Prefer immutable records for message contracts.
- Keep MassTransit consumers thin and delegate behavior to application
  services.
- Use explicit EF Core migrations.
- Use problem-details responses for public errors.
- Do not share EF Core entities across services.

### Python

- Use type annotations for public functions.
- Use async I/O for RabbitMQ and blob operations.
- Keep subprocess construction in one tested adapter.
- Validate message payloads before acknowledging.
- Capture stdout and stderr with bounded buffers.
- Convert yt-dlp output into stable domain errors.
- Do not expose raw exceptions or command lines in published events.
- Use deterministic temporary and artifact naming derived from IDs, not video
  titles.

## Testing Requirements

Use four test layers:

1. Unit tests for validation, state transitions, normalization, prompting, and
   subprocess argument construction.
2. Contract tests validating JSON examples against JSON Schema and checking C#
   and Python compatibility.
3. Integration tests using containerized RabbitMQ, PostgreSQL, and MinIO.
4. End-to-end tests for one submitted video through terminal API result.

Live YouTube tests must be opt-in because external content and extractor
behavior change. Routine CI should use captured, sanitized yt-dlp fixtures and
stub executable behavior. Never commit copyrighted media, authentication
cookies, or secrets.

## Definition of Done

A change is complete only when:

- The requested behavior is implemented.
- Unit and relevant integration tests pass.
- Cross-language contracts remain compatible.
- Database migrations are included when required.
- Error handling and retries are deliberate.
- Logs do not reveal secrets or sensitive paths.
- Documentation and example configuration are current.
- Docker images build successfully.
- Health checks remain meaningful.
- The change does not silently expand yt-dlp access beyond YouTube.

Phase-one completion has additional acceptance criteria in
`PHASE_1_EXECUTION_PLAN.md`.

## Agent Workflow

Before editing:

1. Read the canonical documentation.
2. Inspect the existing implementation and working tree.
3. Identify the owning service and contract boundary.
4. Check whether a contract, migration, or architecture update is required.

While editing:

1. Preserve unrelated user changes.
2. Make the smallest coherent cross-service change.
3. Do not bypass RabbitMQ to make an integration test easier.
4. Do not introduce shared-database coupling.
5. Do not weaken validation or subprocess isolation.

Before handing off:

1. Run the narrowest relevant tests, then broader integration tests.
2. Validate message schemas.
3. Review failure and duplicate-delivery behavior.
4. Report changed files, tests run, and remaining risks.

Do not deploy, publish images, expose services, modify external infrastructure,
or create external resources unless the user explicitly asks.
