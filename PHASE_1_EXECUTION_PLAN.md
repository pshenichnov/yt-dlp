# Phase One Execution Plan: Analyze One YouTube Video

## 1. Objective

Deliver the first complete production-shaped vertical slice of the YouTube
Processing Platform.

A client submits a YouTube video ID or supported video URL. The system
asynchronously extracts a transcript and thumbnail using yt-dlp, stores those
artifacts in S3-compatible blob storage, analyzes the transcript, and exposes a
short description plus bullet points through REST.

This plan defines implementation order, deliverables, tests, and exit criteria.
It does not implement the system.

## 2. Phase-One User Story

As an API client, I want to submit a public YouTube video ID or URL and receive
a job ID so that I can poll the job and later retrieve:

- Basic YouTube metadata
- The extracted transcript
- The video thumbnail
- A short description of the discussion
- Bullet points listing the subjects discussed

## 3. Phase-One Contract

### Input

```json
{
  "video": "https://www.youtube.com/watch?v=abc123def45",
  "preferredLanguage": "en"
}
```

### Immediate response

```http
HTTP/1.1 202 Accepted
```

```json
{
  "jobId": "...",
  "analysisId": "...",
  "status": "queued",
  "statusUrl": "/api/v1/jobs/...",
  "resultUrl": "/api/v1/video-analyses/..."
}
```

### Final result

```json
{
  "analysisId": "...",
  "jobId": "...",
  "video": {
    "videoId": "abc123def45",
    "title": "Example video",
    "channelName": "Example Channel",
    "durationSeconds": 842
  },
  "description": "A concise description of the video discussion.",
  "subjects": [
    "First subject discussed",
    "Second subject discussed",
    "Third subject discussed"
  ],
  "transcript": {
    "language": "en",
    "source": "automaticCaption",
    "artifactUrl": "/api/v1/artifacts/..."
  },
  "thumbnail": {
    "contentType": "image/webp",
    "artifactUrl": "/api/v1/artifacts/..."
  }
}
```

## 4. Explicit Scope Decisions

### Included

- One video per API request
- Manual YouTube captions
- Autogenerated YouTube captions as fallback
- One preferred language
- Best available thumbnail
- S3-compatible blob storage
- Ollama transcript analysis
- Asynchronous job status
- At least two extraction jobs accepted concurrently
- Durable commands, state, and terminal results
- Stable business error codes

### Excluded

- Whisper or other audio transcription
- Full-video download
- YouTube search
- Comments
- Playlists
- Batch submission
- User-selected model or prompt
- Public Internet exposure
- Browser-cookie authentication
- Private, members-only, or age-restricted videos

A public video without a supported caption ends with
`TRANSCRIPT_UNAVAILABLE`.

## 5. Completion Criteria

Phase one is complete when all of the following are demonstrated:

1. A valid video ID is accepted.
2. A valid supported YouTube URL is accepted and canonicalized.
3. Invalid and non-YouTube URLs return `400` problem details.
4. The API returns `202` without waiting for extraction.
5. Job state survives API, orchestrator, and worker restarts.
6. The extractor stores an original caption, normalized transcript, structured
   transcript, and thumbnail in blob storage.
7. RabbitMQ messages contain artifact references, not artifact bytes.
8. The analyzer produces one description and three to ten subject bullets.
9. The final REST result exposes controlled artifact URLs.
10. Duplicate API submissions with the same idempotency key do not create
    duplicate jobs.
11. Duplicate RabbitMQ delivery does not run the same command twice.
12. At least two jobs can be in flight without corrupting temporary files,
    artifacts, saga state, or results.
13. A video without captions fails with `TRANSCRIPT_UNAVAILABLE`.
14. Transient dependency failures are retried and terminal failures are not.
15. Failed messages reach an observable error/dead-letter queue after retry
    exhaustion.
16. Unit, contract, integration, and end-to-end test suites pass.
17. Logs for one job can be traced using the job/correlation ID.
18. No secret, raw command line, stack trace, or local file path appears in a
    public API response.

## 6. Delivery Strategy

Build the smallest end-to-end path first, then harden it. Do not complete each
microservice in isolation before integrating.

Recommended increments:

1. Walking skeleton with fake extraction and fake analysis
2. Real RabbitMQ and persistence
3. Real blob storage
4. Real yt-dlp extraction
5. Real Ollama analysis
6. Reliability and operational hardening

Every increment must leave the system runnable through Docker Compose.

## 10. Milestone 3: Define Contracts Before Consumers

### Tasks

1. Define internal .NET contracts:
   - `VideoAnalysisRequestedV1`
   - `AnalyzeTranscriptV1`
   - `TranscriptAnalyzedV1`
   - `TranscriptAnalysisFailedV1`
   - `JobStageChangedV1`
   - `VideoAnalysisCompletedV1`
   - `VideoAnalysisFailedV1`
2. Define raw Python-boundary schemas:
   - `youtube.video.extract.requested.v1`
   - `youtube.video.extraction.started.v1`
   - `youtube.video.extraction.progressed.v1`
   - `youtube.video.extraction.completed.v1`
   - `youtube.video.extraction.failed.v1`
3. Define common raw-envelope and artifact-reference schemas.
4. Define enums for:
   - Job status
   - Job stage
   - Transcript source
   - Error code
5. Add valid examples and invalid examples.
6. Define AsyncAPI channels, queues, exchanges, and routing keys.
7. Decide backward-compatible evolution rules.
8. Build C# and Python models that validate against the same examples.

### Contract rules

- GUIDs use canonical string form.
- Timestamps are UTC ISO-8601.
- Cross-language properties use lower camel case.
- Artifact references contain no public credentials.
- Error messages are sanitized.
- Unknown optional fields may be tolerated for forward compatibility.
- Required fields cannot be removed within version 1.

### Tests

- Validate all examples against JSON Schema.
- Deserialize every raw command in Python.
- Deserialize every raw event in the .NET bridge.
- Round-trip representative payloads.
- Reject missing version, IDs, type, timestamp, or payload.
- Verify transcript and image bytes cannot appear in terminal messages.

### Exit criteria

- Contract tests run in CI.
- Both languages agree on field names, enum values, optionality, and timestamp
  handling.
- No consumer implementation is required to infer message type from payload
  shape.

## 14. Milestone 7: Implement the Python yt-dlp Extractor

### 14.1 Command consumption

Tasks:

1. Connect to RabbitMQ using `aio-pika`.
2. Declare or verify the expected topology.
3. Use durable messages and publisher confirms.
4. Validate raw JSON against Pydantic models and JSON Schema.
5. Create inbox, execution, artifact, and outbox persistence.
6. Deduplicate by message ID and command ID.
7. Set prefetch and a process semaphore.
8. Create one temporary directory per command.

### 14.2 Subprocess adapter

Tasks:

1. Resolve yt-dlp and FFmpeg from fixed configuration.
2. Verify versions during readiness.
3. Build subprocess arguments as an array.
4. Reconstruct the canonical URL from the validated video ID.
5. Set explicit timeout and cancellation behavior.
6. Capture bounded stdout and stderr.
7. Kill the complete subprocess group on timeout or shutdown.
8. Parse machine-readable metadata rather than human-formatted output.
9. Sanitize diagnostics before persistence or publication.

Unit tests must assert the exact argument array and prove that characters in
input cannot add options or shell operations.

### 14.3 Metadata extraction

Extract and normalize:

- Video ID
- Canonical URL
- Title
- Channel ID
- Channel name
- Upload date
- Duration
- View count
- Like count
- Comment count
- Available caption tracks
- Thumbnail candidates
- yt-dlp version

Store the raw info JSON as an internal diagnostic artifact when enabled. Do not
send it through RabbitMQ.

### 14.4 Transcript extraction

Tasks:

1. Request the preferred language.
2. Discover manual captions.
3. Discover autogenerated captions.
4. Select according to the architecture policy.
5. Download the selected caption as WebVTT.
6. Parse WebVTT into timestamped segments.
7. Remove rolling-caption duplication.
8. Produce normalized UTF-8 text.
9. Produce structured transcript JSON.
10. Calculate checksums.
11. Upload all transcript artifacts.
12. Emit `TRANSCRIPT_UNAVAILABLE` when selection fails.

Do not use regular-expression-only stripping as the WebVTT parser.

### 14.5 Thumbnail extraction

Tasks:

1. Request the best available thumbnail.
2. Detect actual image format and content type.
3. Enforce image-size limits.
4. Upload the original thumbnail.
5. Record checksum, size, and content type.

Thumbnail conversion is unnecessary unless downstream compatibility requires a
single format.

### 14.6 Terminal event

Tasks:

1. Persist the completed extraction and artifact metadata.
2. Write the terminal event to the outbox in the same transaction.
3. Publish with confirmation.
4. Acknowledge the command.
5. Remove temporary files.

For failures:

1. Classify retryability.
2. Preserve diagnostic details privately.
3. Publish a sanitized terminal failure only for business-terminal failures.
4. Allow transport retry/redelivery for retryable failures.

### Tests

- Contract validation
- Inbox deduplication
- Command replay during in-progress and completed states
- Manual-caption preference
- Autogenerated-caption fallback
- No-caption failure
- Requested-language mismatch
- Malformed WebVTT
- Duplicate rolling captions
- Missing thumbnail
- Oversized artifact
- yt-dlp nonzero exit

## 21. Phase-One Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| YouTube changes break yt-dlp | Extraction stops | Pin version, expose version metric, add upgrade/rollback runbook |
| No caption is available | Transcript cannot be produced | Return stable error; add Whisper in a later phase |
| Raw JSON differs between C# and Python | Commands are rejected or misread | JSON Schema, examples, bidirectional contract tests |
| Duplicate RabbitMQ delivery | Duplicate work or results | Inbox/outbox, stable command IDs, unique constraints |
| Large transcripts exceed model context | Incomplete summary | Segment-aware map-reduce analysis |
| Local Ollama is slow | Long analysis stage | One controlled consumer, timeouts, provider abstraction |
| N100 resource pressure affects Immich | HomeLab instability | Conservative concurrency, load test, monitor memory and swap |
| NTFS artifact volume behaves poorly | Artifact corruption or latency | Verify MinIO behavior, checksums, backups, keep databases on ext4 |
| Message contains large artifact | Broker pressure | Blob references only and message-size tests |
| Temporary files remain after crash | Disk exhaustion | Per-command directories and scheduled cleanup |
| MassTransit licensing is unresolved | Implementation or deployment blocker | Decide and record before scaffolding |
