# YouTube Processing Platform Architecture

## 1. Document Status

- Status: accepted architecture; phase-one vertical slice implemented
- Last updated: July 25, 2026
- Working system name: YouTube Processing Platform
- Solution prefix: `YouTubeProcessing`

This document describes the target microservices architecture and the
phase-one vertical slice. It is intentionally implementation-oriented while
remaining independent of specific source-code details.

## 2. System Purpose

The platform asynchronously extracts and analyzes public YouTube content.
Clients submit work through REST and poll REST resources for status and
results. Processing is coordinated through RabbitMQ so HTTP requests do not
remain open while yt-dlp or an LLM is running.

Phase one accepts one YouTube video ID or URL and returns:

- Canonical video metadata
- A transcript artifact in blob storage
- A thumbnail artifact in blob storage
- A concise description
- Bullet points describing the subjects discussed
- Durable job status and stable failure information

The architecture also reserves boundaries for later YouTube search, comments,
audio transcription, bulk analysis, and semantic indexing.

## 3. Architectural Drivers

1. Work may take seconds or minutes and must not be coupled to an HTTP request.
2. Multiple jobs must run concurrently with workload-specific limits.
3. yt-dlp is a fast-changing external CLI and must be isolated.
4. .NET and Python need a stable, language-neutral integration contract.
5. RabbitMQ provides at-least-once delivery, so consumers must be idempotent.
6. Transcripts and thumbnails are too large or inappropriate for broker
   messages and must be stored as blobs.
7. Workflow state must survive process and host restarts.
8. HomeLab-N100 has four CPU cores and limited memory, requiring conservative
   concurrency.
9. The public API must not expose internal paths, broker details, or secrets.
10. The design must permit independent scaling without creating unnecessary
    phase-one services.

## 4. Scope

### 4.1 Phase-one scope

- REST submission using a video ID or supported YouTube URL
- REST job-status retrieval
- REST analysis-result retrieval
- Asynchronous workflow orchestration
- yt-dlp metadata extraction
- Manual-caption extraction
- Autogenerated-caption fallback
- Transcript normalization
- Thumbnail extraction
- Blob storage for transcript and thumbnail artifacts
- Transcript analysis using a configurable provider
- Short description and subject bullet points
- Concurrent processing
- Retry, dead-letter, inbox, and outbox behavior
- Structured logs, aggregate dependency and consumer health checks, and basic metrics

### 4.2 Phase-one non-goals

- Global or channel-specific YouTube search
- Comment extraction
- Playlist processing
- Bulk API submission
- Full-video download
- Audio extraction and Whisper fallback
- Semantic or vector search
- User interface
- Public unauthenticated access
- Multi-region deployment
- Exactly-once processing

## 6. Container and Service Model

### 6.1 YouTubeProcessing.Api

Type: ASP.NET Core Web API

Responsibilities:

- Validate and canonicalize video input
- Create the public job and analysis identifiers
- Enforce idempotency
- Persist job and analysis read models
- Publish the initial internal event using the MassTransit bus outbox
- Consume job-status and result events
- Serve job and result resources
- Generate controlled artifact download URLs
- Apply authentication and API rate limits

Owned data:

- `Jobs`
- `VideoAnalysisResults`
- `ArtifactReadModels`
- API idempotency records
- MassTransit bus outbox tables

The API does not run long-running processing.

### 6.2 YouTubeProcessing.Orchestrator

Type: .NET worker service

Responsibilities:

- Host the `VideoAnalysisStateMachine`
- Persist saga state
- Send extraction and analysis commands
- Apply workflow timeouts
- Handle stage progress and terminal events
- Publish API-facing job events
- Bridge typed internal contracts to raw Python integration contracts
- Bridge raw Python integration events to typed internal events

Owned data:

- Video-analysis saga state
- Orchestrator inbox/outbox tables

The orchestrator is the authority for workflow state. The API read model is a
projection of orchestrator events.

### 6.3 youtube-processing-extractor

Type: Python worker service

Responsibilities:

- Consume raw JSON extraction commands
- Validate command schema and supported options
- Deduplicate commands
- Invoke yt-dlp safely
- Parse yt-dlp metadata
- Select manual captions or autogenerated captions
- Normalize transcript content
- Extract the best available thumbnail
- Upload artifacts to blob storage
- Publish progress and terminal raw JSON events
- Record inbox/outbox state

Owned data:

- Extractor inbox
- Extractor outbox
- Extraction execution records
- Temporary local files

The service reconstructs a canonical URL from `videoId`. It never executes a
URL or CLI arguments supplied verbatim by a client.

### 6.4 YouTubeProcessing.Analyzer

Type: .NET worker service

Responsibilities:

- Consume typed analysis commands through MassTransit
- Deduplicate commands
- Retrieve normalized transcript artifacts
- Enforce transcript size and content limits
- Chunk long transcripts
- Call the configured transcript-analysis provider
- Validate structured provider output
- Persist the analysis
- Publish completion or failure events

Owned data:

- Analyzer inbox/outbox
- Analysis execution and model metadata

The initial provider is the non-interactive Codex CLI authenticated through a
personal ChatGPT account. Provider-specific code is hidden behind an
`ITranscriptAnalyzer` port so API-key or other hosted providers can be added
later.

### 6.5 Infrastructure containers

- RabbitMQ with management UI restricted to trusted administration networks
- PostgreSQL
- MinIO for local S3-compatible blob storage
- Codex CLI in the Analyzer image
- Optional OpenTelemetry Collector
- Optional Prometheus and Grafana after core phase-one functionality

One PostgreSQL server may be used initially, but services receive separate
databases or schemas and credentials.

## 8. Phase-One End-to-End Flow

### 8.1 Success sequence

```text
Client
  │ POST /api/v1/video-analyses
  ▼
API
  │ validate input
  │ create job + outbox record in one DB transaction
  │ return 202 Accepted
  │
  └── publish VideoAnalysisRequestedV1
           ▼
     Orchestrator saga
           │ create saga; publish JobStageChanged(Extracting)
           │ send raw ExtractYouTubeVideoV1
           ▼
     Python extractor
           │ inbox/deduplicate
           │ run yt-dlp for metadata/captions/thumbnail
           │ normalize transcript
           │ upload transcript and thumbnail
           │ persist outbox
           └── publish YouTubeVideoExtractedV1
                         ▼
                   Orchestrator saga
                         │ record artifact references
                         │ publish JobStageChanged(Analyzing)
                         └── send AnalyzeTranscriptV1
                                      ▼
                                Analyzer
                                      │ fetch transcript
                                      │ run subscription-authenticated Codex
                                      │ validate and persist result
                                      └── publish TranscriptAnalyzedV1
                                                   ▼
                                             Orchestrator
                                                   │ complete saga
                                                   └── publish
                                                       VideoAnalysisCompletedV1
                                                               ▼
                                                             API
                                                               │ update projection
                                                               ▼
Client ◄── GET /api/v1/jobs/{jobId} and /video-analyses/{analysisId}
```

### 8.2 Failure flow

Any stage emits a typed failure containing:

- Stable error code
- Sanitized message
- Retryability classification
- Failed stage
- Attempt number
- Optional artifact references already produced

The orchestrator either:

1. Waits for transport-level delayed redelivery, or
2. Transitions the saga to `Failed` and publishes
   `VideoAnalysisFailedV1`.

The API projection exposes a safe problem description and preserves partial
artifact metadata for administrative diagnosis. Public clients do not receive
raw stderr, stack traces, or local paths.

## 9. Workflow State Model

### 9.1 Saga states

```text
Initial
  → Extracting
  → Analyzing
  → Completed

Initial | Extracting | Analyzing
  → Failed

Initial | Extracting | Analyzing
  → CancelRequested
  → Canceled
```

Phase one may expose cancellation only after the core success path works, but
the state model reserves it.

### 9.2 Public status

Public status is deliberately simpler than saga state:

- `queued`
- `running`
- `completed`
- `failed`
- `cancelRequested`
- `canceled`

Public stages:

- `validating`
- `queued`
- `extractingMetadata`
- `extractingTranscript`
- `extractingThumbnail`
- `storingArtifacts`
- `analyzingTranscript`
- `savingResult`

Progress is approximate. Stage changes are authoritative; numeric percentage
is informational.

## 11. Input Canonicalization

Canonicalization occurs at the API boundary:

1. Trim the input.
2. If it matches the supported video-ID form, accept it as a candidate ID.
3. Otherwise parse it as an absolute HTTPS URI.
4. Require a supported YouTube host.
5. Extract exactly one candidate video ID.
6. Reject playlist-only, channel, and search resources.
7. Store the original sanitized input for audit.
8. Send only `videoId` to downstream services.

The extractor performs a second validation and builds:

```text
https://www.youtube.com/watch?v={videoId}
```

Successful yt-dlp metadata is authoritative for canonical video identity.

## 12. RabbitMQ and MassTransit Design

### 12.1 Internal .NET messages

.NET services use typed MassTransit messages with the standard MassTransit JSON
envelope:

```text
Content-Type: application/vnd.masstransit+json
```

Internal contracts live in versioned contract assemblies. Commands are sent;
events are published.

### 12.2 Python boundary

The Python boundary uses raw JSON:

```text
Content-Type: application/json
```

MassTransit raw JSON serialization and deserialization are configured only for
integration endpoints. An integration adapter translates between raw JSON and
internal typed messages.

### 12.3 Phase-one topology

Command queue:

```text
youtube.extract-video.commands.v1
```

Event topic exchange:

```text
youtube.extract-video.events.v1
```

Routing keys:

```text
youtube.video.extraction.started.v1
youtube.video.extraction.progressed.v1
youtube.video.extraction.completed.v1
youtube.video.extraction.failed.v1
```

Internal MassTransit endpoints:

```text
youtube-processing-orchestrator
youtube-processing-analyzer
youtube-processing-api-projection
```

Dead-letter/error queues are configured for every consumer endpoint.

## 13. Blob Storage

### 13.1 Provider

Application services depend on an S3-compatible abstraction. MinIO is the
phase-one deployment, but service code does not use MinIO-specific concepts
beyond configuration.

Bucket:

```text
youtube-artifacts
```

Suggested keys:

```text
videos/{videoId}/{extractionVersion}/metadata/info.json
videos/{videoId}/{extractionVersion}/transcript/{language}/manual-caption.vtt
videos/{videoId}/{extractionVersion}/transcript/{language}/automatic-caption.vtt
videos/{videoId}/{extractionVersion}/transcript/{language}/transcript.txt
videos/{videoId}/{extractionVersion}/transcript/{language}/transcript.json
videos/{videoId}/{extractionVersion}/thumbnail/thumbnail.{extension}
analyses/{analysisId}/{analysisVersion}/analysis.json
temporary/{commandId}/...
```

Keys are based on identifiers, not untrusted video titles.

### 13.2 Artifact metadata

Every artifact reference contains:

- Artifact ID
- Bucket or storage alias
- Object key
- Content type
- Size
- SHA-256 checksum
- Created timestamp
- Artifact kind
- Retention classification

Blob upload completes before a success event is made durable.

### 13.3 Consistency

PostgreSQL, RabbitMQ, and blob storage do not share a distributed transaction.
The producer therefore:

1. Uploads an immutable object.
2. Verifies object metadata or checksum.
3. Persists the execution result and outbound event in one database
   transaction.
4. Publishes the event through the outbox.

If the process stops after upload but before the database commit, the object is
an orphan. A maintenance job removes old unreferenced temporary objects.

## 14. Transcript Extraction

### 14.1 yt-dlp strategy

The extractor uses yt-dlp machine-readable output and explicit output paths.
The exact command may evolve with pinned yt-dlp versions, but it must:

- Skip full-video download
- Write metadata JSON
- Retrieve manual captions
- Retrieve autogenerated captions as fallback
- Restrict requested languages
- Retrieve the best thumbnail
- Avoid arbitrary output templates derived from the title
- Run inside a command-specific temporary directory

Metadata extraction and artifact download may be split into multiple
subprocesses when that produces clearer error handling and deterministic
caption selection.

### 14.2 Caption selection

Selection order:

1. Exact requested language, manual
2. Compatible requested-language variant, manual
3. Exact requested language, autogenerated
4. Compatible requested-language variant, autogenerated
5. Terminal `TRANSCRIPT_UNAVAILABLE`

Machine-translated caption variants are excluded in phase one.

### 14.3 Normalization

WebVTT normalization:

- Decode as UTF-8
- Parse cues rather than stripping lines heuristically
- Preserve timestamped segments
- Remove duplicate rolling-caption fragments
- Remove markup while preserving spoken text
- Normalize whitespace
- Preserve meaningful paragraph boundaries when possible
- Produce deterministic output for identical input

Normalization must not reinterpret or summarize the transcript.

## 15. Transcript Analysis

### 15.1 Provider abstraction

```text
ITranscriptAnalyzer
└── AnalyzeAsync(TranscriptAnalysisRequest, CancellationToken)
    → TranscriptAnalysisResult
```

Initial implementation:

- Provider: Codex CLI with ChatGPT authentication
- Default model: `gpt-5.6-sol`, configurable
- Prompt version: `video-analysis-v2`
- Concurrency: one request initially to protect account usage limits

The model setting is configuration, not part of public API input.

### 15.2 Prompt behavior

The system prompt requires:

- Use only supplied metadata and transcript
- Return concise, neutral language
- Produce a short description when `summary` is selected
- Produce three to ten distinct subject bullets when `topics` is selected
- Avoid speculation
- State uncertainty when transcript evidence is insufficient
- Return structured JSON

Expected provider response shape:

```json
{
  "description": "A concise description supported by the transcript.",
  "subjects": [
    "First subject discussed",
    "Second subject discussed",
    "Third subject discussed"
  ]
}
```

The analyzer validates:

- Non-empty description
- Description length limit
- Three to ten non-empty bullets
- Bullet length limit
- No unexpected fields when strict mode is enabled

Invalid output is retryable only for a small configured number of attempts.

### 15.3 Long transcripts

The analyzer must not silently truncate.

Use a map-reduce strategy when the transcript exceeds the configured context
budget:

1. Split on segment or paragraph boundaries.
2. Summarize each chunk into candidate subjects.
3. Combine chunk results into one final description and deduplicated subject
   list.
4. Store chunking metadata with the result.

Chunk inputs and intermediate model responses are not public API fields.

## 17. Idempotency and Delivery

### 17.1 API idempotency

An `Idempotency-Key` is scoped to an authenticated client. Reusing a key with
the same normalized request returns the original job. Reusing it with a
different request returns `409 Conflict`.

### 17.2 Message idempotency

- Each command has a stable `commandId`.
- Consumers persist inbox receipt.
- Duplicate in-progress commands do not launch another subprocess.
- Duplicate completed commands cause the stored terminal event to be
  republished or acknowledged according to outbox state.
- Duplicate events do not advance a saga twice.

### 17.3 Outbox

.NET services use MassTransit’s transactional outbox. The Python service
implements a database-backed outbox publisher with RabbitMQ publisher confirms.

Delivery remains at least once.

## 18. Retry, Timeout, and Error Model

### 18.1 Error taxonomy

Terminal examples:

- `INVALID_VIDEO_ID`
- `VIDEO_UNAVAILABLE`
- `VIDEO_PRIVATE`
- `VIDEO_AGE_RESTRICTED`
- `TRANSCRIPT_UNAVAILABLE`
- `UNSUPPORTED_TRANSCRIPT_LANGUAGE`
- `TRANSCRIPT_TOO_LARGE`
- `ANALYSIS_CONTENT_INSUFFICIENT`

Retryable examples:

- `YOUTUBE_THROTTLED`
- `YOUTUBE_NETWORK_ERROR`
- `BLOB_STORAGE_UNAVAILABLE`
- `RABBITMQ_PUBLISH_FAILED`
- `ANALYZER_TIMEOUT`
- `ANALYZER_INVALID_RESPONSE`

Internal unexpected errors use a safe generic public code while retaining a
private diagnostic ID.

### 18.2 Timeouts

All values are configuration. Initial targets:

- Metadata/caption/thumbnail extraction: 5 minutes
- Individual blob operation: 60 seconds
- Analyzer request: 5 minutes
- Overall extraction stage: 10 minutes
- Overall analysis stage: 15 minutes
- Overall job: 30 minutes

### 18.3 Retry policy

- Short immediate retries only for brief connection errors
- Delayed redelivery with exponential backoff for remote dependency failures
- No unbounded retry
- Dead-letter/error queue after exhaustion
- Stable terminal event after business-terminal errors

## 19. Concurrency and Scaling

### 19.1 Initial HomeLab limits

- API: normal ASP.NET asynchronous concurrency
- Orchestrator: concurrency limited by saga persistence capacity
- Extractor: two concurrent commands
- Analyzer: one concurrent Codex operation
- RabbitMQ prefetch aligned with consumer concurrency

These limits protect the four-core N100 and existing Immich workload.

### 19.2 Horizontal scaling

- API replicas are stateless beyond PostgreSQL.
- Orchestrator replicas share saga persistence and RabbitMQ.
- Extractor replicas compete on one command queue.
- Analyzer replicas compete on one command queue.
- Blob storage and PostgreSQL remain shared infrastructure.

No client or orchestrator change is required to add worker replicas.

## 20. Security

### 20.1 API

- Authenticate all non-health endpoints.
- Rate-limit job submission.
- Validate input before persistence and again before execution.
- Restrict allowed YouTube hosts and resource types.
- Return problem details without implementation secrets.

### 20.2 Extractor

- Run as non-root.
- Use `create_subprocess_exec`, never a shell.
- Use a fixed executable path.
- Build all yt-dlp arguments from trusted configuration.
- Construct the canonical video URL from a validated ID.
- Set process and output limits.
- Use a unique temporary directory.
- Do not follow arbitrary local or remote paths from yt-dlp output.

### 20.3 Infrastructure

- Separate credentials per service.
- Keep RabbitMQ, PostgreSQL, MinIO, the Analyzer, and internal services on a private
  Docker network.
- Bind the API to Tailscale for the initial HomeLab deployment.
- Store secrets outside source control.
- Do not reuse Immich databases, users, networks, or credentials.

## 21. Observability

### 21.1 Correlation

The REST job ID is the message `correlationId`. Propagate it through:

- HTTP logs
- MassTransit headers
- Raw JSON envelopes
- Python logs
- Blob artifact metadata
- Codex process exit status and bounded duration, without prompts or credentials

Use `messageId` and `causationId` to reconstruct the message chain.

### 21.2 Health

Every service exposes:

- Liveness: the process event loop is functioning
- Readiness: mandatory dependencies are reachable

The extractor readiness check verifies configured executable presence and
version without contacting YouTube.

### 21.3 Metrics

Phase-one metrics:

- Job counts by terminal status
- Queue depth and consumer utilization
- Stage latency
- Retry and dead-letter count
- yt-dlp exit-code classification
- Caption source distribution
- Thumbnail and transcript artifact sizes
- Blob operation latency
- Analysis duration and model failures
